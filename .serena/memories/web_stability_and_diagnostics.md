Web stability design (Nov 2026). Root causes of laggy/desynced web UI were: free heap only ~18 KB idle (8 parallel GETs => OOM reboot), EEPROM commit on every slider change, FastLED.show() pushing all MAX_LEDS (300 => ~9 ms CPU) every frame, global 100 ms request throttle returning 429 silently, 5 s polling of 3 endpoints overwriting sliders, verbose per-request logs (Serial + WS + String ring buffer).

Current rules:
- Persistence is debounced in main.cpp loop(): handlers set settingsChanged; loop moves it to settingsSavePending and calls saveLEDState() only after SETTINGS_SAVE_DELAY_MS (3000) of no changes. Still never save in handlers.
- No request throttle anymore (checkThrottle removed). All POST body handlers start with `if (index + len != total) return;`. POST routes use shared no-op onRequest `onBodyRequestDone`.
- GET handlers and "/" call rejectIfLowMemory(): 503 + Retry-After when ESP.getMaxFreeBlockSize() < 4096.
- WebSocket /ws/logs: max 2 clients (MAX_WS_CLIENTS); history = last 25 entries via logger.getHistoryJson().
- Logger (src/logger.*): fixed char ring buffer LOG_RING_SIZE (<=30) x LOG_MESSAGE_MAX_LEN 80, UTF-8 safe trim, WS broadcast skipped when !ws->availableForWriteAll(). Keep handler logs to one short line; no per-GET logging.
- LED output length: syncLedCount() (led_modes.cpp) calls FastLED[0].setLeds(leds, numLeds), blanking the tail once when shrinking; called every frame before effects. Power off: effects only fill black, main shows one black frame then skips show().
- Diagnostics (src/diagnostics.*): DiagSnapshot over 5 s window (loopsPerSec, maxLoopMs, ledFps, maxLedFrameMs, slowestTask, minFreeHeap, minMaxFreeBlock, eepromSaves, lastSaveMs); warnings rate-limited to 1/10 s. GET /api/debug exposes these plus freeHeap, maxFreeBlock, heapFragmentation, resetReason, wsClients.
- Web UI (webpage.h JS): all requests go through a single-flight queue apiRequest(method, endpoint, data) with 6 s timeout; queued POSTs with the same key (endpoint + modeId/index/id) are coalesced (latest wins). apiCall() kept as wrapper. Polling via pollState() every 10 s, skipped when tab hidden, queue busy, any *Modal open, or user acted in last 5 s (markUserAction). Periodic poll fetches backlight data only in backlight mode. Mode grid re-rendered only if archived set changed. Browser time is pushed only if device time invalid or drift > 60 s. Red #connectionBanner shows on network failure.
- UI redesign (webpage.h): no CDN/Tailwind — single self-contained page (~60 KB) with inline CSS variables, dark mobile-first layout, works without internet. Layout: sticky header (status dot + round power button) → segmented Гирлянда/Подсветка → brightness card → garland panel (now-playing card with ◀ ▶ and ⚙, modes grid where tapping a card selects and ⚙ opens settings, archived modes in collapsible <details id=archiveDetails>, inline auto-switch delay/random saved on change — old settingsModal removed) or backlight panel (palette with "✎ Изменить" edit mode, + tile to add, animations grid, inline auto-switch) → device card (LED count, schedule) → logs <details>. Modals are bottom sheets `.sheet-overlay.open` (openSheet/closeSheet, backdrop click/Escape close). Grids use event delegation (data-mode-id / data-gear). WebSocket logs connect only while logs section is open. Schedule sheet: <input type=time>, action segmented control, device clock fetched every 30 s and ticked locally.
- Local UI preview without device: temp/ui_mock_server.py (in-memory mock of /api/*, serves page from src/webpage.h on http://localhost:8765). temp/ is gitignored.
- Time sync (src/main.cpp): static-IP WiFi.config() MUST pass DNS (dns1 = gateway, dns2 = 8.8.8.8) — without it DNS is 0.0.0.0 and neither NTP nor HTTP fallback resolve hosts (was the cause of timeValid=false). configTime() uses 3 servers (NTP_SERVER, pool.ntp.org, time.cloudflare.com). HTTP fallback parses the `Date` header of http://connectivitycheck.gstatic.com/generate_204 (parseHttpDate + daysFromCivil, no timegm in newlib); worldtimeapi.org was dropped (resets connections). Fallback retried every 300 s from loop() only while time is invalid.
- Boot speed (src/main.cpp setup): no blocking NTP wait (SNTP runs in background; loop() logs "Time synchronized" once and starts HTTP fallback after 15 s, then every 300 s). Green WiFi flash is 150 ms. WiFi fast connect: channel + BSSID cached in RTC user memory (WifiRtcCache at block offset 96 — blocks 0..31 are eboot's OTA command, do not use), WiFi.begin(ssid, pass, channel, bssid) skips the scan (~1.1 s instead of ~3.8 s); falls back to full scan after 5 s and clears the cache. RTC survives soft reset/OTA, not power loss. WiFi events (associated/got IP/disconnected + reason) and "setup() started at N ms" are logged with millis() for boot diagnostics. Gratuitous ARP was tried and did not help — not the bottleneck.
